    AgentHarbor functional review¶

    Review date: 2026-09-20. Application: my_ai_app/. Baseline commit: 59239fc.

    Verdict¶

    AgentHarbor has a useful support workflow and a substantial working application foundation. Company workspaces, access restrictions, document ingestion, source lookup, draft revision and human approval work in the tested scenarios. It is a local pilot, not ready for an unattended public launch. The most important product promise, accurate AI answers grounded in company documents, remains unverified with a live model.

    The supplied OpenAI key was added only to the ignored backend .env. API and worker were restarted. The configured model remains gpt-5.5; semantic embeddings remain disabled. The first real OpenAI request returned HTTP 429, credit_balance_exhausted, type insufficient_quota, after 3.96 seconds. One subsequent support generation exercised the application's provider failure path and produced a failed job with no draft. No successful live AI answer or embedding was obtained. Billing cost cannot be established from these failed responses.

    OpenAI documents quota-related 429 failures separately from transient rate limiting: the operator needs to check API credits and spending limits. See OpenAI error documentation. The key being present does not establish account quota, model access or service health. Since it was shared in chat, revoke and replace it locally after this review; do not put its replacement in a message or tracked file.

    Confirmed weaknesses and priorities¶

    1. High: signup can succeed before the account is visible to login¶

    Reproduced in three immediate API signup/login attempts: registration returned 201, immediate login returned 401. In the instrumented attempt, waiting 200 ms made the same credentials succeed. This is a real timing failure that ordinary browser smoke missed.

    The likely cause is the session lifecycle: app/db/session.py commits after yielding, and app/api/deps.py uses the default dependency scope. Confirm transaction completion relative to response delivery and ensure successful mutation responses are sent only after commit. Do not fix it by adding frontend sleeps. Add a regression that observes real transaction visibility, plus streaming/session lifecycle checks before changing dependency scope globally.

    The extended review deliberately paces later mutations by 100 ms to continue inspecting other features; those successful checks do not disprove this transaction timing issue. The first login attempt is unpaced.

    2. High: retrieval misses normal customer paraphrases¶

    Test document: "Refund requests are accepted within fourteen days of purchase. Contact support with your order number."

    refund policy retrieved the document. Can I get my money back? returned zero sources. Current keyword mode therefore cannot reliably retrieve by meaning. This can produce unnecessary escalation even when the answer is present.

    Enable and evaluate the implemented hybrid embeddings path after credits are available, reindex documents, and use a representative question set. This is a proposed improvement, not a verified semantic-search result. No pgvector installation is required for the current bounded JSON-vector implementation.

    3. Medium: provider status and errors are misleading¶

    Readiness and the general smoke script label the provider healthy based only on key presence, even while the actual account has no credit. Support Usage similarly reports provider_configured, not actual usability. Provider failure becomes: "Processing failed. Check provider configuration and worker health, then retry."

    Expose configuration status separately from the last verified provider result. Map billing, invalid credentials, model access and timeouts to safe actionable messages. Do not issue paid calls on every readiness poll. Retrying an exhausted balance cannot fix it.

    4. Medium: duplicate uploads consume capacity¶

    Uploading identical bytes with the same filename created a second document and ingestion job. A checksum is stored, but the upload flow does not use it for deduplication. Add workspace-scoped duplicate handling while preserving explicit version replacement. This matters for storage, duplicated search evidence and future embedding costs.

    5. Medium: active PDF rejection is incomplete¶

    A synthetic text PDF created with pypdf's add_js was accepted and its text extracted. The current parser checks /OpenAction and page /AA, but this fixture stores JavaScript through a name tree.

    This test did not execute JavaScript or demonstrate code execution. It demonstrates that the current active-content rejection policy is incomplete. The parser is a subprocess with limits, not an OS sandbox or malware scanner. Expand validation with fixtures for named actions, annotations and embedded content, and choose deployment-appropriate isolation/scanning before accepting arbitrary public uploads.

    6. Medium: useful backend errors can disappear in the client¶

    Code review found domain errors shaped as {error: {message: ...}} in app/api/exception_handlers.py, while frontend/src/lib/api-client.ts reads top-level detail or message. Such errors fall back to "Request failed". This is a source-level finding; a separate browser assertion for every affected error was not run. Normalize the API error contract and add a client regression.

    7. Release limitations remain¶

    • Citation ID validation proves the source exists, not that it supports every generated claim. Live grounding, contradictions, injection resistance and refusal quality still need evaluation.
    • No helpdesk connector: employees must paste questions and copy approved replies manually.
    • No verified worker supervision, deployment alerts, backup restore drill, multi-user load target or billing reconciliation.
    • Source removal prevents later source access, but existing draft text/history can retain derived information; retention needs a documented product policy.
    • Public first-admin bootstrap needs review before exposure. The user service mentions FIRST_ADMIN_EMAIL, but searching backend/app found only the comment, not an enforcement implementation.
    • Existing deprecation and accessibility warnings remain. Passing lint with warnings is not an accessibility certification.

    Honest product assessment¶

    The strongest part is the workflow around an answer: scoped knowledge, source visibility, revision conflicts, permissions, and human approval. The product already handles more of that workflow than a basic chatbot demo. Document retrieval followed by grounded drafting is RAG, including the current keyword retrieval variant.

    The weakest part is proven usefulness: retrieval currently misses ordinary paraphrases, real answer quality is still unmeasured, and there is no direct helpdesk integration. The signup race and misleading provider status also undermine user trust. I would use this for controlled internal testing with synthetic or approved data, but would not market it as a reliable production support agent yet.

    What is needed next¶

    1. Available OpenAI API credits/spend allowance and access to the configured model. No additional provider key is needed for the currently selected OpenAI integration; replace the exposed key locally.
    2. Restart API and worker after replacing credentials. Confirm one bounded real request succeeds before running a small answer-quality evaluation.
    3. Evaluate direct answers, paraphrases, missing evidence, conflicting policies, document prompt injection, source removal and cancelled generation. Record answer grounding, exact usage and latency. Credits may reveal further model/configuration errors that this review could not reach.
    4. Fix the confirmed timing and error-reporting defects, then repeat the affected flows.
    5. For a meaningful product-quality verdict, supply a sanitized company document set and representative customer questions with expected answers. Synthetic fixtures alone cannot establish customer accuracy.

    Other infrastructure credentials are needed only if enabling additional services such as real email delivery, OAuth, payments or helpdesk connectors. Those external flows were not tested here.

    Reproduction¶

    With API, frontend and native worker running, use the commands in quality requirements and support runbook.

    The added diagnostic script is my_ai_app/backend/scripts/review_support_flows.py. From the backend:

    PowerShell
    $env:DEBUG='true'
.\.venv\Scripts\python.exe scripts/review_support_flows.py

    It prints JSON check results, including expected diagnostic findings, and cleans its own unique records. Review its final findings array; a completed diagnostic run is not an all-pass release gate. It requires support enabled, keyword mode and configured provider-key presence for the no-evidence fallback path, but does not submit a source-backed provider generation by default.

    --provider-failure submits one source-backed generation and expects failure; use it only when explicitly testing a known provider outage. Do not run that option to evaluate a healthy provider. The SDK may make internal retries; one application job is not a guarantee of one upstream HTTP attempt.

    This review left runtime defects unchanged so the report reflects the observed application. Changes are the ignored local key, this report, reproducible diagnostic script, and documentation of the new verification status. No commit or push was made.
